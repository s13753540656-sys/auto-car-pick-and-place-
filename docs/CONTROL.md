# 控制方案与资料边界

## 当前可以确认的内容

原项目说明采用 STM32 控制，自主完成行驶、抓取、搬运、放置；控制和电控由团队另一组负责。仓库没有提供 STM32 工程、板卡型号、驱动协议、接线、传感器配置、标定或运行日志。因此本页是后续整理与改进的设计建议，不是现有固件实现说明。

## 建议的任务状态流程

| 状态 | 任务 | 建议退出条件 | 异常处理原则 |
| --- | --- | --- | --- |
| 待机 / 检查 | 确认通信、机构初始状态及任务许可 | 所需反馈有效，收到明确开始命令 | 不直接驱动进入自动流程，记录缺失反馈 |
| 行驶 | 到达目标附近 | 位置或任务阶段得到确认 | 到达超时或反馈失效时停止推进 |
| 对准 | 将目标置于夹爪允许入口范围 | 对准条件持续成立，机构不与环境干涉 | 目标丢失时终止接近，按已验证策略恢复 |
| 下托 / 合围 | 执行抓取动作 | 实际反馈确认到位及抓取状态 | 超时、堵转或未抓到时不直接开始搬运 |
| 抬升 / 保持 | 进入可搬运位姿 | 位姿与保持条件确认 | 负载状态异常时停止任务推进 |
| 搬运 | 移动至放置区域 | 到达放置条件 | 根据验证过的保持与停车策略处理目标松脱 |
| 放置 / 退出 | 降低、释放并退出目标空间 | 释放与机构退出确认 | 释放失败时禁止强行拖离 |
| 完成 / 故障 | 报告结果或等待人工处理 | 明确的复位与重新开始条件 | 保留故障原因，不自动无条件循环重试 |

每个状态应有明确的反馈来源、有效期、到位判定、超时值和退出动作。不能把“发出电机命令”当作“已经到位”。超时和速度数值需来自实际硬件与试验，本仓库不提供猜测值。

## 可优先落实的控制改进

1. **底盘与夹爪动作互锁**：确认允许移动的机构位姿，避免目标未保持或机构未退出就进入下一步。
2. **反馈失效处理**：通信中断、陈旧反馈、限位异常、目标丢失分别产生明确故障原因；不延用过期的“到位”信号。
3. **故障后的载荷保持**：根据执行器、制动和机械保持结构决定每个轴的动作。底盘停止与负载保持应分别定义，不能未经核实统一断电导致目标下落。
4. **分阶段调试**：先记录手动与空载状态，再验证单次抓取，最后联调搬运放置，保留每阶段的真实日志。
5. **参数和记录版本化**：将型号、标定、参数、CAD 版本和固件提交关联，便于判断问题来自机构还是控制变化。

## 接入固件前需要团队补充

| 资料 | 应包含内容 |
| --- | --- |
| 工程与工具链 | STM32 具体型号、工程文件、编译器和版本、构建及烧录说明 |
| 电控接口 | 引脚与信号定义、电源、驱动器、通信协议和更新周期 |
| 执行器约束 | 实际型号、限位、正方向、允许范围、使能 / 停止 / 保持策略 |
| 状态反馈 | 对准、位置、抓取、释放状态如何获得，时间戳和失效条件 |
| 日志 | 状态切换时间、目标与实际状态、故障码、恢复操作、运行结果 |

这些资料齐备后才能审查代码、构建固件并判断具体参数优化。目前没有可执行固件的构建或烧录验证结果。
